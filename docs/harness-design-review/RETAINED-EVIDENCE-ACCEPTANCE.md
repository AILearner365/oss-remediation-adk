# Evidence-boundary acceptance catalogue

This development-only runner provides retained-evidence, read/edit, and controlled Intent-recovery scenarios. The retained-command case tests whether the model uses a real harness-issued reference to recover a decision fact omitted from a command excerpt. It does not run the OSS remediation orchestrator, evaluate vulnerability-remediation quality, or deliver anything. Run it separately from comparable frozen Experiment 1 evaluations.

The runner accepts `--scenario` and `--trials 1..10`; every trial has an independent workspace and session. `--workspace-parent` retains artifacts in either offline or live mode; absent that option, offline workspaces are temporary. Live mode requires an explicit folder. A, E1 and E2 have explicit paid `--live` modes. C is offline-only. B is tested deterministically and observed opportunistically within A. D uses the production integration tests below. Each trial writes `artifacts/acceptance-result.json`, including failures and the workspace location. Each retained-command live result reports retrieval, no submission, rejection count, exhaustion, acceptance, selection consistency, source citation, trace path and terminal error separately; E1/E2 use the controlled checks and outcomes documented below. The scorer reconstructs section-only repairs and verifies the exact merged bytes against the accepted journal section/hash before inspecting candidate and provenance; later rejected calls cannot revise that score. Oversized ADK interaction arguments are loaded from their hash-bound retained artifacts. The mechanical criteria are a conservative screen: keyword patterns cannot verify arbitrary prose, and ambiguous choices require manual review rather than a confident pass.

## Controlled malformed-Intent recovery (E1 and E2)

These reusable cases are implemented in `scripts/intent_recovery_scenarios.py` and selected through the existing runner. They use the real `JournalLifecycle`, `DeveloperCapabilitySet.submit_cycle_intent`, production phase protection, normal `default_agent_session_factory` / ADK path, and the existing `run_until_intent` loop. No second orchestrator, delivery adapter, target repository, tool alias or production prompt change is introduced.

The fixture writes a short generic diagnostic report with an issued evidence reference and prepares substantive decision data. E1 removes `section` from the populated selected answer; E2 removes `answer` from the candidate and selected objects without adding `content`. It invokes the supported capability directly and records `controlled_intent_seed` with fixture origin and no model session ID. This consumes checkpoint attempt 1. It does **not** inject function calls or responses into ADK session internals. The model subsequently receives the actual submitted payload, capability response, production continuation message and normal questionnaire; it receives no corrected answer objects. Evidence is supplied directly because retrieval is not the boundary under test.

Required setup: repository dependencies from `autonomous_oss_remediation_agent/requirements.txt`, a supported local isolation backend for workspace setup, and (live only) approved Cloud Shell ADK/Gemini credentials. The existing CLI loads the optional root `.env` without replacing process values. Use the project's installed Python environment; no provider or budget overrides are needed. Keep workloads sequential and check RAM/disk first. Live execution is opt-in and belongs to Cloud Shell. Windows offline checks remain supported through the existing platform-specific workspace backend; Windows → Cloud Shell remains the fallback. Unavailable execution does not remove the runnable scenario; retain its blocked result.

Offline commands (no model calls; supported Windows or Cloud Shell environments):

```bash
python -m scripts.retained_evidence_acceptance --scenario intent-missing-section --workspace-parent ./intent-recovery-offline
python -m scripts.retained_evidence_acceptance --scenario intent-missing-answer --workspace-parent ./intent-recovery-offline
python -m unittest tests.unit.test_intent_recovery_scenarios tests.unit.test_evidence_boundary_acceptance tests.unit.test_decision_journal -v
```

The offline CLI checks the real seed rejection, draft retention and authoritative-edit denial. When those checks pass it reports `offlineMechanics=PASSED`, while `outcome` and `controlledLiveIntegration` remain `NOT_EXERCISED`; exit zero means offline mechanics succeeded only. The regression suite additionally uses scripted models through real ADK callbacks to test resubmission/continuation, full and section-only repair, exhaustion, failure/blocking, accepted-byte verification and retention. These are deterministic checks, not autonomous live evidence.

Acceptance checks are defined before execution:

- E1 rejects `answers[4].section` as missing; E2 rejects `answers[3]` / `answers[4]` with their section names and missing `answer`. Callback and continuation must agree and must not invent a `content` field.
- The actual draft snapshot equals the unaffected valid submitted sections (four for E1, three for E2). An explicit authoritative-write probe is denied with `PHASE_CAPABILITY_UNAVAILABLE`, and the repository digest stays unchanged.
- The seed is exactly one rejected checkpoint attempt, before any model session. Subsequent model calls run in one session and cycle 1; checkpoint-attempt events must agree with lifecycle counters. A supported full resubmission is as acceptable as a section-only repair; `sectionOnlyRepairObserved` describes the accepted call, not a mandatory gate.
- A live resubmission must lead to accepted Intent; replay must match its exact journal bytes and content hash. The scorer projects the explicitly labeled seed into the shared replay input only. Stored audit events and ADK session history preserve the distinction between fixture and model actions.
- Existing fixture bounds remain one cycle, 80 engineering tool calls, 60 model calls per turn, ten checkpoint attempts/continuation turns, and 1,800-second turn / 7,200-second overall limits. ADK enforces the model-call cap. Checkpoint submissions and the denied phase probe are accounted under existing production rules, not counted as engineering tool calls. Results record configured limits, elapsed time, tool calls, attempts, turns and session IDs. Limits are not increased for recovery.

Reporting is explicit: `PASSED` requires all controlled checks and verified model resubmission/acceptance without terminal error; `FAILED` means an assertion, fixture, capture or model-recovery failure, including existing budget/checkpoint exhaustion; `BLOCKED` means unavailable isolation, credentials, provider transport/service or session infrastructure, with the exact error retained; `NOT_EXERCISED` means the live boundary was not run. Setup failures still retain `acceptance-result.json`; unavailable execution remains pending/blocked. Live failure/blocking exits nonzero. `naturalAutonomousRecovery` is always `NOT_EXERCISED` for these deliberately seeded cases, even when controlled integration passes.

Artifacts in each printed workspace: `artifacts/fixture/diagnostic.txt`, `fixture/seed.json` (payload, callback, continuation, actual draft, denial, limits and seed counters), `fixture/model-input.txt`, `events.jsonl`, `agent/decision-journal.md`, any retained `agent/interactions/*.json`, and `acceptance-result.json`. Preserve these selected artifacts, not temporary homes/caches. Inspect trace and substantive accepted content as well as the mechanical result. Successful capture verifies this integration boundary; it does not establish engineering reasoning quality or autonomous recovery reliability.

For an ordinary model-led run, natural malformed-Intent recovery is exercised only when the trace shows a model-originated malformed submission, actual rejection and subsequent accepted repair. Otherwise report **NOT EXERCISED**. Do not repeat unchanged workloads to provoke an error. The earlier `run-20261003T042625Z-1d44e715` retained-command run accepted valid Intent on attempt 1; its malformed-submission/rejection/repair paths remain unexercised.

## F/G. Complete finding coverage and conflicting release evidence

`scripts/reasoning_boundary_scenarios.py` extends the same runner and `run_until_intent` continuation loop. Both cases use normal `AGENT_INSTRUCTION`, Q1–Q5, `DeveloperCapabilitySet`, `default_agent_session_factory` and journal acceptance/replay. There is no injected/corrected Intent, nominated candidate, tool alias, second agent, or production policy change. Fixture facts are synthetic and never runtime policy. Scoring stops at the accepted decision; a production model turn can continue into disposable fixture edits after acceptance, which cannot improve the accepted decision's score. No delivery adapter or real target repository is involved.

| Case | Decision boundary | Required semantic review |
|---|---|---|
| F `finding-coverage` | Production `canonical_task_to_solve` serializes three applicable findings on one synthetic dependency. A published, compatible lower version fixes two; a higher same-line version additionally fixes the third. The task and support record supply facts, without a selected candidate. | Account for all findings, assess the **selected** candidate's complete/partial coverage and constraints, check its cited support against observed sources, preserve validation limits. A plausible partial fix must not be called complete. |
| G `evidence-conflict` | A repository note supplies an unsupported expectation that a synthetic runtime's 4.x release is custom. An authoritative fixture publisher record establishes availability; project adapter compatibility is expressly unevaluated. Fixture-originated search returns a bot challenge and fetch returns publisher content through real research capabilities and issued references. | Reconcile the expectation with authoritative availability, do not turn blocked search into absence, preserve compatibility uncertainty, and assess the selected next action and its actual citations. Release existence alone cannot establish suitability. |

G deliberately controls evidence acquisition before the model session; `controlled_evidence_acquisition` marks that origin, consumes two ordinary tool calls, and does not seed ADK tool history or Intent. The model may research/read further. This is **controlled evidence with autonomous model decisions**, not natural source discovery, proof of a model's internal prior, real release research, or natural end-to-end remediation. F uses the OSS task serializer, including its conditional Spring Boot policy; that does not make the synthetic gateway a Spring Boot component.

Setup: installed project requirements, supported workspace isolation, approved ADK/Gemini credentials for live mode. Existing root `.env` loading and Windows → Cloud Shell fallback apply. Limits are unchanged from A/E: one cycle, 80 shared calls, 60 model calls per turn, ten checkpoint attempts/continuations, existing 1,800/7,200-second limits.
